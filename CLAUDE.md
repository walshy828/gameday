# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"Dodgeball Tracker" (repo name: tournament-gamedayapp) — a live tournament gameday app: division standings, schedule, admin match entry, and a synchronized round timer/scoreboard, deployed via Docker.

## Commands

- `npm start` — run the server (`node server/index.js`), serves both the API and the static frontend on `PORT` (default 8888).
- `npm run build:css` — one-shot Tailwind build (`src/input.css` → `public/dist/output.css`, minified).
- `npm run watch:css` — Tailwind in watch mode during frontend work.
- `docker-compose up --build` — build and run the containerized app (maps port 8888, loads `.env`).
- `npm run stress -- --url <base> --users 150 [--ramp 30] [--duration 300] [--burst] [--staff-token <t>]` — read-only load test (`server/scripts/stressTest.js`, needs the `socket.io-client` dev dependency): virtual parents load a division, hold a live socket, poll My team/clock, resume from lock screen; prints p50/p95/p99 per endpoint, errors, dropped sockets, pushes received, and a verdict. It never writes; to exercise live pushes, save results against a throwaway DB while it runs. Run it before the event, not against the live server during it.

There is no test suite or linter configured in this repo.

Frontend has no bundler/build step of its own — `public/js/*.js` are loaded directly as ES modules by `public/index.html`; only CSS goes through Tailwind.

## Architecture

**Split backend architecture — two different paths for reading data:**
- The Express server (`server/index.js`) exposes a small JSON API (`/api/allData`, `/api/divisions`, `/api/standings`, `/api/validateAdmin`, `/api/saveMatchResult`) backed by Firebase Realtime Database as the primary data source (`server/sheets.js`, despite its name, reads/writes Firebase — Google Sheets is a secondary, best-effort mirror).
- The frontend (`public/js/main.js`, `public/js/navigation.js`) *also* loads the Firebase client SDK directly (`firebase-app-compat.js`, `firebase-database-compat.js`, `firebase-auth-compat.js` via CDN in `index.html`) and talks to Firebase directly in the browser for: fetching division names, live-watching a division for realtime updates (`watchDivision`), and all round-timer/scoreboard state (firebase mode: `timer/byDivision/{division}` RTDB nodes, bound by `public/js/timerFirebase.js`). Initial data loads (standings/schedule) go through the Express API (`getAllData` in `public/js/api.js`); live delta updates and the timer bypass the server entirely.
- When editing data-loading logic, check whether you're in the server-API path or the direct-Firebase browser path — they are separate and not interchangeable.

**Round clock (per-division, with ownership):** each division has its own clock/round (`timer_state` row in local mode, `timer/byDivision/{division}` in firebase mode), so viewing another division never touches the one being run. Each clock has one *controller* tab (`controllerId`/`controllerName`, tab identity from `public/js/timerClient.js`); control actions from other tabs are refused (HTTP 409 in local mode) until they "Take over" — UI in `timerControlsUI.js`. In local mode all transitions go through `server/timerControl.js` → `Store.mutateTimer` (row lock + column-level update), `POST /api/timer/:action` is superadmin-only, and the *server* performs after-round/reset at expiry (clients never post expiry). `timerOverlay.js` auto-syncs the round only from the owning tab and warns/confirms when controlling a division other than the one last run.

**Triple write-through on match result save** (`POST /api/saveMatchResult` → `server/index.js`): a single save writes to three systems, each independently, with the request still succeeding if some fail (see `server/sheets.js:saveMatchResult` and `server/index.js`'s route handler):
1. Firebase RTDB schedule entry + a `history` push log (source of truth for the live UI).
2. Google Sheets, columns H:L + a JSON history blob in column M (only if `SPREADSHEET_ID`/Google service account env vars are set — otherwise silently skipped).
3. MariaDB (`server/mariadb.js` → `server/db.js`), an audit-log style insert into `gameday_submissions` (only if the DB pool is configured/reachable).

Data key structure in Firebase RTDB: `dodgeball-tournament/divisions/{sheetName}/{standings|schedule}`, where `sheetName` is the division name used as the RTDB key directly (division names must avoid `. # $ [ ] /`).

**Result discrepancies (superadmin):** a referee-submitted result (`adminWinner`/`adminPlayersRemaining`) that differs from the official one (`winner`/`playersRemaining`, set only once official). Detection is the pure `public/js/discrepancy.js` (shared by browser and server); `server/discrepancies.js` scans all divisions, `GET /api/discrepancies` and `POST /api/discrepancies/dismiss` are superadmin-only, and dismissals are shared via `Store.getDiscrepancyDismissals`/`setDiscrepancyDismissal` keyed on a value fingerprint (a changed result re-opens it). Clients refetch on the data-less `discrepancyUpdate` socket ping (plus `syncStatusUpdate` and a 30s poll). UI is quiet by design except for playoffs: a **playoff winner change** (`isUrgentDiscrepancy` = playoff match + reported winner ≠ official winner; players-left differences don't count) is pinned to the very top of Admin (`#discrepancy-urgent`, red), turns the ADMIN tab dot red, adds "⚠ Winner changed — see top" on that court-board tile, and makes Start round / End round confirm first (`confirmDisputes` in `courtReady.js`). Everything else sits in a one-line, collapsed "Needs review (N)" strip under the court board, above the filters (`#discrepancy-passive`, open state per browser in `localStorage.discrepancyPassiveOpen`). Plus the gate badge, row chips, and a per-browser alert level (Dot only [default]/Full/Off) in Setup; Off hides both areas. The ntfy push only fires for urgent ones. Below those, an "All games" / "Court N games" heading (`#admin-games-heading`) starts the filters + game list. Optional playoff push: set `NTFY_URL` (+ `NTFY_TOKEN`). **Edit history:** `GET /api/matchHistory?division=&index=` (any referee or superadmin token) returns every submission for a match oldest first (`Store.getMatchHistory`: local `match_history`, firebase `schedule/{i}/history`), each with `official` = the superadmin's save really set the official result (server-checked `forceOfficial`). Shown on demand only: a collapsed "Edit history" link in the match entry modal (reported games) and an "Edit history" button per Needs review item.

**Roster (superadmin):** the Roster footer tab (before Admin) is the app's version of the Registrations sheet's Apps Script "Team Management" tool — team list, then per-team roster with waiver status and remove/add/rename/move player + Paid/Sub Division edits. `server/rosterCore.js` is a line-for-line port of the pure planner in `RM_Core.gs` (builds a plan of ops/changes/warnings; keep it in step with the Apps Script so outcomes match), `server/rosterSheets.js` reads the sheet into that shape and executes the plan via the Sheets API (writes serialized by an in-process lock, then re-reads and verifies), and `GET /api/roster`, `POST /api/roster/preview|apply` are superadmin-only. Frontend is `public/js/roster.js`. Requires `ROSTER_SPREADSHEET_ID` and the registration sheet shared with the service account as Editor (`ROSTER_TZ` optional, default America/New_York, for change-log timestamps). The sheet stays the source of truth; change-log lines say "(Gameday App)". **Sheets quota discipline** (`server/rosterSheets.js`, keep it when changing the adapter): the Sheets API allows ~60 reads + ~60 writes/min for the whole service account, so reads are one `batchGet` for all tabs, what the screens show is cached server-side until Refresh / a write / `ROSTER_CACHE_SECONDS` (default 300), and the cache is NEVER used to place a write (every write re-reads the rows it touches, because forms and Apps Script can shift rows). Each action is ONE atomic `spreadsheets.batchUpdate` (cells, log line, row insert/delete, formula copy-down, new columns/tab); the post-write check re-read doubles as the cache refresh. Tab ids, log headers and formula columns are cached (15 min); calls are throttled to `ROSTER_MAX_REQUESTS_PER_MIN` (default 50) and retried on 429. **Team check-in** (port of Apps Script v15): `setCheckin` / `addCheckinNote` / `getCheckinLog` in `server/rosterSheets.js` write `Checked In` / `Check-In Time` / `Check-In By` on the team's Registrations row (columns created on first use) plus an append-only `Check-In Log` tab; `/api/roster/checkin*` routes. It is off by default behind the shared feature setting `checkinEnabled` (Setup toggle, stored via `Store.getFeatureSettings`/`updateFeatureSettings`, not the sheet's own switch). "Check-In By" is the superadmin's reporter name. Season Reset does not clear the `Check-In Log` tab.

**Follow a team + "My team" card (public, no login):** `public/js/follow.js` stores the followed team per division in `localStorage` (`followTeam:<division>`, `__none__` = "not now"; only leaves the phone as an anonymous count for Live now, below), asks once after a division is picked on the gate (`maybeAskFollow`), and fires a `followchange` window event (main.js re-renders standings/schedule/playoffs/card). `public/js/myTeam.js` renders the card into `#my-team-card-standings` and `#my-team-card-schedule` (re-rendered after every data load/live update via `renderMyTeam()` in main.js): playing now / 📣 head to Court N (board staging with a record) / ✓ on court ready / game over (official result, else "result pending") / byes with time off from round times ("2 bye rounds · about 30 min off · back at …") / pool play done (record + rank) / playoffs (seed, round name from `cleanRoundLabel` minus the time, else `defaultRoundLabel(depth)`; opponent or "winner of A / B · playing now on Court N"; advanced; eliminated with "Top N finish" + "stick around for the Final"; finalists; champions). Playoff progress uses OFFICIAL results only. The court-board rules live in the pure `public/js/courtBoard.js` (`deriveBoard`), shared by the MC board, referee bar and this card. The card reads `GET /api/courtStatus/public?division=` (no login, no referee names: board record + ready marks); the `courtStatusUpdate` socket event is a data-less nudge (staff refetch the authed route, the card the public one). Highlights: gold ★ row in standings (`standings.js`), gold left edge on the team's schedule rows (`window.isFollowedTeam` in `schedule.js`), `.bracket-team-row.followed` in the bracket (`playoffs.js`, which also opens the team's sub-division and scrolls to it on first look and exports its bracket helpers for the card). The card's "My games" toggles the schedule's team filter.

**Live now / usage (superadmin, Setup's first card):** in-memory only, built to cost ~nothing on game day. Every tab's existing Socket.IO connection is one "connection" (`public/js/presence.js` opens one even in firebase mode); the tab emits a tiny `presence` message ONLY when something changes (auth token, division, followed team, court, current view, hidden/shown; a 5s local check, no network unless changed) plus on every (re)connect. `server/presence.js` keeps a `Map` socketId → `{role, division, team, court, view, visible, device}` (role resolved server-side from the token via `chatRoleOf`, re-checked only when the token changes; no-login = `public`, shown as "Participants & parents"; `device` is a random per-browser id in `localStorage.presenceDevice` so tabs vs phones can be told apart; no names/IPs), deletes on disconnect, and a 60s timer samples totals + health (event-loop delay p99 via `monitorEventLoopDelay`, CPU %, RSS, API requests and 5xx per minute from the `requestCounter` middleware) into a 12h ring buffer plus the day's peak. `GET /api/usage` (superadmin) computes the summary in one pass; `public/js/usage.js` polls it every 10s only while Setup is on screen in a visible tab. Health pill: Healthy / Busy (lag ≥ 80 ms, CPU ≥ 60 %, any 5xx) / Strained (lag ≥ 250 ms or CPU ≥ 85 %). Everything resets on restart.

**Traffic priority (load shedding, superadmin, Setup → Live now → 🚦):** `server/loadShield.js`, in memory (restart = Normal). Tiers: `staff` (superadmin, admin, raffle, concessions — never throttled) > `parent` > `public` (no sign-in). Each socket sits in a `tier:<tier>` room (joined/updated in `server/presence.js` when its token's role resolves). Modes: **Normal** (public GET `/api/allData`, `/api/divisions`, `/api/announcements` share a 2s read-through cache that also collapses concurrent misses), **Ease** (cache 15s; `broadcastDivisionUpdate` sends instantly to staff/parents and batches the newest snapshot to public at most every 5s per division; public My team polling 2x slower), **Protect** (cache 60s; public pushes every 30s, parents every 5s; polling 4x slower; confirm prompt). Staff bypass the cache by sending their token (`staffToken()` in `api.js`). Caches are invalidated in `server/socket.js` on division/announcement/feature/sync broadcasts, so in local mode cached reads are not stale; in firebase mode writes don't go through those broadcasts, so a cached public read can be up to the TTL old. Lowering to Normal flushes batched pushes. Clients learn the level from the `trafficMode` socket event and the `presence` ack (`trafficPollFactor()` in `presence.js`; staff always 1). Routes `GET/POST /api/traffic` (superadmin); also returned in `/api/usage`.

**Setup page layout** (`#settings-view` in index.html, ordered most-used first, with quick-jump chips `.setup-jump`): Live now (Live now card, Signed-in users) → Event day (Announcements, Court Ready, Team Check-In, discrepancy alerts, Champion Celebration) → Sync & results (Google Sheet Sync, Auto-Update Official Results) → Configuration, set once (Max players left, Roster Editing, Role passwords) → Seasons & data (Seasons, Division data, Raffle backup, Danger zone). Put new cards in the group that matches how often they're touched.

**Court switching (court managers):** the court picked at login (`App.state.selectedCourt`) is the referee's court for the day — header, crew chat label, session record, Court Ready — and is separate from the `admin-court-select` view filter (changing the filter does NOT move them). The admin header's "Court N ▾" chip opens a bottom-sheet switcher (`openCourtSwitcher` → `switchCourt` in `admin.js`), which updates `selectedCourt` (sessionStorage + `lastAdminCourt`), moves the filter, points Court Ready at the new court, warns if the old court is still waiting for teams, and fires an immediate heartbeat. The heartbeat carries the court (`/api/session/heartbeat` → `Store.touchSession(sessionId, court)`, applied only to `admin`-role sessions). Nudge: saving a result for a game on a different court shows "Saved · you're on Court X" with a one-tap "Switch to Court Y". Bye footers on the Admin tab collapse to a one-line "N teams on bye ▸" (`byesShown` in `admin.js`): collapsed by default for court managers, expanded for the superadmin; one tap flips every round, remembered per browser per role in `localStorage` (`adminByesShown:court|superadmin`).

**Court readiness (optional, `courtReadyEnabled`):** Setup → "Court Ready" switch (off by default; turning it off clears everything). The board is **round-based** and **derived on every render** (`public/js/courtReady.js` `deriveBoard`), never stored: it shows one *board round* B in one of two phases. `playing` (after ▶ Start round or the clock's Start): each court with a game in B is IN PLAY or ✓ FINAL (with result); a court that finishes early stays FINAL — next-round statuses never show mid-round. `staging` (after End round →, or automatically once every game in B is reported): courts show B's teams in large type for announcing, WAITING FOR TEAMS / READY; referees can only mark ready now. Courts with no game in B show NO GAME THIS ROUND. A "last round" strip lists unreported games from rounds before B ("11:15 round: 3 of 4 final · waiting on Court 2 …"), then "✓ … all scores in". The server (`server/courtStatus.js`, in-memory only, never the sheet or a DB) keeps just: ready **marks keyed by division + game** (`gameKeyOf`: round|court|team1|team2) and per division the **board record** `{ round, phase, prevRound, at }` with one level of undo. Without a record (never used / server restart) B = earliest unreported round, `playing` if the clock runs its main segment on it. Clock links: ▶ Start round records the start and, if this tab can run the clock, sets its round label (`window.setClockRound` → backend `setCurrentRound`) and clicks `#start-btn`; the clock's own Start also records the start (extra listener); End round steps the clock's label to the next round; when the clock for B stops or enters the after-round break, End round turns gold and pulses ("⏱ Time's up"). MC alerts: time's up, all courts ready, round complete, last scores in. **Rounds = start times:** the board groups games by the time inside the round label (`slotKey`/`slotOf` in `courtBoard.js`), so "Round of 16 · 12:25 PM" (Pool A) and "Quarterfinals · 12:25 PM" (Pool B) run as ONE board round on all courts; tiles get a "Pool A · Quarterfinals · P5" caption when a round mixes brackets. The board record stores the time; the clock still gets a real round label (`firstRawOf`), set on Start round and End round. **Squeeze-ins:** when a court is free (its game is final mid-round, or it has no game this round), the MC board offers "⚡ Court 3 is free · squeeze in …" for a not-yet-played game from a later *short* round (≤ 2 games) whose teams are known and not playing right now. Starting it stores an early record `{ gameKey, court }` (server `setEarly`, actions `early`/`unearly`); the game then shows IN PLAY · SQUEEZED IN on that court for the MC, referee bar (with Report) and the public card ("Playing now · Court 3"), uses `courtFor(g)` for its court everywhere, and once reported its round auto-skips if nothing else is left in it. **Owed scores:** each board row carries `owed` = that court's unreported games from rounds before B (MC ended the round / time ran out first). The referee bar then shows only "Court N · 11:15 score not reported · Report 11:15 score" (Mark ready is hidden, and `setReady` refuses it for non-superadmins) until it's reported; the MC tile shows "⚠ 11:15 score missing" + Report, and a marked court with an owed score doesn't count toward "N of M ready" / all ready. **Two refs / slow network:** `setMark` keeps the FIRST ready tap (a later or retried tap gets `already: {by, at}` and the phone says "already marked ready by Maya", no Undo); a referee's Undo sends `onlyIfAt` so it removes only the mark it made (`kept` otherwise), plain "Not ready" always clears; the mark POST times out after 8s ("No connection … tap again", then a refresh), the button shows "Marking…" while in flight, the ref bar shows "Marked by X", and a status read that was in flight when a write landed is dropped (`writeSeq`) so the court doesn't flicker back. Routes: `GET /api/courtStatus` and `POST /api/courtStatus/mark` (admin token), `POST /api/courtStatus/round` (superadmin: start/end/undo/clearMarks/clearAll); live via `courtStatusUpdate` socket event + 20s poll.

**Court issue flags (always on, no setting):** a referee "raises their hand" for their court. Admin view `#court-issue-panel` (`public/js/courtIssues.js`): "✋ Flag an issue on Court N" → bottom sheet where one tap on Dispute / Injury / Other raises it (no note) → a sticky red card ("Waiting for the MC…" / "✓ <name of whoever acknowledged> is on the way", "Take flag down"; while it's up the Court Ready ref bar gives up its sticky spot via `refFlagUp()`). The MC (superadmin) gets a red stack fixed just above the tab bar on EVERY view (`#court-issue-alerts`, minimisable) with **On my way** (ack, superadmin only) and **Resolved ✓** (clear); a new flag beeps/vibrates/notifies and reminds every 45s while any flag is unacknowledged; the court-board tile gets a red "✋ Flag up" line. Server `server/courtIssues.js`: in-memory only, one flag per physical court (a second raise keeps the original time/ack), `clear` takes the flag `id` so a stale tap can't clear a newer flag; recent clears are kept so the ref's phone can say "the MC took the flag down". Routes `GET /api/courtIssues`, `POST /api/courtIssues/raise|ack|clear` (any referee/superadmin token; ack superadmin-only); live via the data-less `courtIssueUpdate` socket nudge + 20s poll. A raise also pushes to ntfy when `NTFY_URL` is set (`server/ntfy.js`, shared with the playoff discrepancy push).

**No ties in playoffs:** `ALLOW_MATCH_TIE` only applies to pool play. `isPlayoffGame` (`public/js/discrepancy.js`: `P1`… in the match column or round label) hides the tie tile in match entry (with a "Playoff game — no ties" note), the submit refuses it, and `/api/saveMatchResult` returns 400 for a tie on a playoff game.

**Raffle (raffle manager role):** a fourth login tier for selling raffle tickets from a phone: `RAFFLE_PASSWORD` (env) signs in as `isRaffle`, whose name becomes the sale's Seller; superadmin can use it too. The Raffle tab (`public/js/raffle.js`: Sell / Sales / Report) talks to `GET /api/raffle` and `POST /api/raffle/sale`, gated by `requireRaffle`; raffle managers get no match entry, timer or chat. `server/raffleSheets.js` reads/writes the "Gonk Dodgeball Raffle Manager" spreadsheet (`RAFFLE_SPREADSHEET_ID`, shared with the service account as Editor; `RAFFLE_TZ`/`RAFFLE_CACHE_SECONDS` optional) and appends to its `Sales` tab exactly like the sheet's Apps Script `submitSale_`, so Station tabs, Drawing, Lookup and Dashboard keep working. `public/js/raffleLogic.js` is the pure pricing/ticket-allocation port of that script (shared by browser preview and server; keep it in step with the script). **Quota discipline:** one `batchGet` of Config+Rolls+Sales is the single cached snapshot (default 60s, Refresh bypasses after 10s) behind all three tabs, so search/filter/report are computed client-side and cost nothing; a sale costs exactly one fresh read (inside the in-process lock, never the cache, because ticket numbers come from the sheet's current state) plus one `values.batchUpdate` (Sales rows + any roll flipped to Full), and that read becomes the new cache. A `clientId` per submission makes double taps return the original receipt. Roster and raffle share one throttle (`server/sheetsQuota.js`, `SHEETS_MAX_REQUESTS_PER_MIN`, default 50/min per kind). **Offline-first selling:** `public/js/raffleStore.js` (same pattern as concessions) saves every sale to localStorage (`rf:*`) BEFORE any network, and the phone picks the ticket numbers itself from the last roll snapshot plus its own unsynced sales (`view()`), then posts an ordered outbox to `POST /api/raffle/sale` with explicit `lines` + `soldAt`. `server/raffleSheets.js` records those exact ranges (`deviceLines`), never refuses an overlap with another sale (tickets are already torn): it writes it with a `CHECK TICKETS` note and returns `conflicts`. A retry is idempotent on `clientId` via the in-memory map AND `RaffleDb.findByClientId` (survives server restarts; a `pending` row is matched against the sheet's receipts). Rejected (400) sales stay in the on-phone log. The Device tab shows waiting/failed/overlapping sales and exports them (CSV, TSV matching Sales columns A:P, plain text). The raffle login is also kept in `cn:auth` (role `raffle`) so a reload offline returns to selling. Two phones selling the SAME roll offline can overlap, so give each seller their own roll. Voiding, bundles/colors/rolls and winner drawing stay in the sheet. **Database backup:** every sale is also saved to MariaDB `raffle_sales` (`server/raffleDb.js`, table auto-created, also in `schema.sql`) BEFORE the sheet write and flipped to `synced`/`failed` after it, so a row left `pending` means the sheet write's outcome is unknown; the DB step is best-effort (a sale still goes through if the DB is down, and the seller sees a warning). Superadmin Setup → bottom card → Raffle backup page (`public/js/raffleBackup.js`) lists the DB rows (no Sheets calls, CSV export) and `GET /api/raffle/reconcile` (`server/raffleReconcile.js`, pure `compare()`) diffs them against the Sales tab by receipt with one forced Sheets read (missing either side, field differences, pending/failed; read-only). Receipt numbers restart if the Sales log is cleared, so the DB can hold a reused receipt (flagged; newest compared).

**Concessions (concessions role) and Seasons:** a fifth login tier: `CONCESSIONS_PASSWORD` (env) signs in as `isConcessions`; superadmin can use it too and reaches Concessions and Raffle from buttons in the gate's Admin Panel (their tabs are hidden for superadmin). MariaDB only, no sheet: `server/concessionsDb.js` (tables `concession_items`/`concession_settings`/`concession_sales`, auto-created, also in `schema.sql`), routes `GET/POST /api/concessions*` gated by `requireConcessions` (503 without a DB). Sale lines store name/price as sold; items are hidden, never deleted; the server recomputes totals. **Offline-first:** `public/js/concessionsStore.js` writes every sale to localStorage first (`cn:*` keys), then posts an ordered outbox (sale/void ops, idempotent on client-generated `clientId`; a 400 parks the op in `cn:failed`, network/5xx/401 retry later). `public/sw.js` + `offline.js` cache the app shell and CDN scripts (network-first same-origin, cache-first CDN; never `/api` or `/socket.io`); the concessions login is also kept in `localStorage` (`cn:auth`, 24h) so an offline reload goes straight back to the stand (`checkLoginStatus`, `openConcessionsFromGate`). UI: `concessions.js` (Sell/History + shell), `concessionsReport.js`, `concessionsItems.js` (items/prices/order/categories + Venmo username/note; needs a connection), `concessionsUi.js`. Venmo QR is `https://venmo.com/<user>?txn=pay&amount=..&note=..&audience=private` drawn locally by the vendored qrcode lib; the note never lists items. **Seasons** (`server/seasons.js`, table `seasons`, one `is_current`): concession sales and `raffle_sales` rows are stamped with a `season_id`; only the superadmin starts a new season (Setup → Seasons card, `public/js/seasons.js`, `/api/seasons*`); reports/history show the current season, past ones are selectable. Raffle tickets themselves still live in the raffle sheet (reconcile compares the sheet against all seasons' DB rows). Note `lines` is a reserved word in MariaDB 11, so it is backtick-quoted in `raffleDb.js`.

**Auth model**: no sessions/JWTs for the app's own auth — `ADMIN_PASSWORD`/`SUPERADMIN_PASSWORD`/`PARENT_PASSWORD` (env) are checked server-side in `/api/validateAdmin`, which returns a deterministic SHA-256 token (`password + SECRET_SALT`) that the client resends as `authToken` on subsequent writes (`isValidToken` in `server/index.js` recomputes and compares). Superadmin additionally receives a Firebase custom auth token (`Fb.createCustomToken`) so the browser's Firebase client SDK can authenticate for direct RTDB writes (e.g. timer controls). Three tiers: `ADMIN_PASSWORD` (court referees — match entry + crew chat), `SUPERADMIN_PASSWORD` (tournament manager — timer/announcements/sheet sync + everything Admin has), `PARENT_PASSWORD` (crew chat only, posts labeled "Parent · name"; gated by `requireChatAuth` rather than `requireAdmin`/`requireSuperAdmin`).

**Frontend module structure** (`public/js/`, loaded as native ES modules, no bundler):
- `main.js` — app bootstrap, global `showStatus`/`loadData`, direct-Firebase timer/round-control logic (`timerRef`, round next/prev), and `exposeGlobals()` which attaches selected module functions to `window` so inline `onclick=` handlers in `index.html` can reach them.
- `navigation.js` — division dropdown (desktop select + mobile scroll buttons), view switching (`standings`/`schedule`/`admin-entry`), filter dropdowns.
- `admin.js` — admin login/logout, match entry modal, save-result flow.
- `schedule.js` / `standings.js` — rendering schedule/standings tables and the admin standings ticker/pager.
- `celebration.js` — championship banner/confetti when a playoffs final completes.
- `api.js` — thin fetch wrappers for the Express `/api/*` routes (relative to `window.location.origin`, no separate API base config needed for same-origin deploys).
- Global app state lives in a plain `App` object defined inline in `index.html` (`App.state`, `App.data`, `App.config`, `App.settings`, `App.refresh`), not in any JS module — read it there before assuming a field exists.

**Styling**: Tailwind, custom theme colors (`primary`/`secondary`/`accent`/`admin-bg`) in `tailwind.config.js`; source in `src/input.css`, compiled output committed at `public/dist/output.css` and served with an explicit MIME-type-safe route (`server/index.js`) in case a hosting proxy mis-serves it as `text/html`.

## Environment

Configured via `.env` (see `docker-compose.yml`, loaded with `dotenv`): Firebase service account (`FIREBASE_PROJECT_ID`/`GOOGLE_CLIENT_EMAIL`/`GOOGLE_PRIVATE_KEY`/`FIREBASE_DATABASE_URL`), optional Google Sheets mirror (`SPREADSHEET_ID` + same service account), optional MariaDB (`DB_HOST`/`DB_USER`/`DB_PASSWORD`/`DB_NAME`), app auth (`ADMIN_PASSWORD`/`SUPERADMIN_PASSWORD`/`PARENT_PASSWORD`/`SECRET_SALT`), and optional roster sheet (`ROSTER_SPREADSHEET_ID`), optional raffle (`RAFFLE_PASSWORD` + `RAFFLE_SPREADSHEET_ID`), optional concessions (`CONCESSIONS_PASSWORD`, needs MariaDB), optional GA4 event tracking (`GA_MEASUREMENT_ID`/`GA_API_SECRET`). Each integration degrades gracefully (features log/skip) when its env vars are absent, except Firebase, which is required — `server/firebase.js` will throw at import if the service account vars are missing.
